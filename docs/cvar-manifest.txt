# cvar-manifest.txt - the reviewed verdict for every registered-but-unread cvar.
#
# Checked by tools/dead-cvars.py. A cvar nothing reads looks exactly like a
# working setting: you set it, it takes the value, and the game ignores it. That
# has cost this tree real bugs twice - g_spawnItemWeapons was registered,
# exposed as a gamerule, documented, set to 0 in the shipped instagib configs,
# and read by no code at all, so instagib servers kept spawning weapons.
#
# THESE CVARS ARE STAYING. Nearly all of them are Quake Live's own, transcribed
# from the real binary's cvar table so that a factory file, a server config or a
# stock client finds the name and the flags it expects. Wiring one up means
# implementing the feature behind it; deleting the name would only make the
# absence harder to find later.
#
# So this file is the point of keeping them. A flat list of 240 is the same list
# every time and nobody reads it, which means the 241st - the one somebody added
# last week and forgot to wire - disappears into it. Here, the 240 are a backlog
# you can grep by verdict, and anything unread that is NOT in this file is
# UNCLASSIFIED and fails the build.
#
# Format:  VERDICT<tab>cvar_name<tab>module, flags - reason
#
#   QL-FEATURE  a Quake Live feature this port has not implemented. The cvar is
#               real and so are its flags; the behaviour is what is missing.
#               This is the wiring-up backlog.
#   NETWORKED   the value goes out in an info string or is read-only
#               informational. Unread by our C is correct and complete - the
#               consumer is a remote client or the server browser.
#   QL-ASSET    read only by Quake Live's own pak00 menus or HUD, which this
#               tool cannot see without being pointed at a QL install.
#   GAP         nothing reads it, nothing remote sees it, and there is no Quake
#               Live feature behind it. A real defect - fix or remove.
#
# HOW THESE VERDICTS WERE REACHED, because it matters when you rely on one:
# they are assigned BY FLAG CLASS, not by investigating each cvar. A QL-FEATURE
# row says "this carries CVAR_GAMERULE / CVAR_USERSAVE and our code never reads
# it", which is a fact. It does NOT say anyone has worked out what the feature
# does or how hard it would be. Treat a row as a starting point for that work,
# not as its result. When you do investigate one, replace the reason with what
# you found.
#
# Nothing here is GAP. That is not a claim the tree has no dead cvars of its own
# - it is that every unread cvar currently in the tables came in with the Quake
# Live port rather than being invented here, checked against the root commit.
# A GAP row is what a newly added one should get.
#
# Regenerate the rows (verdicts are then re-applied by hand):
#     tools/dead-cvars.py --list
